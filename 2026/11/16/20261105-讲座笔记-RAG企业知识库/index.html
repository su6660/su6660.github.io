讲座笔记：RAG 与企业知识库搭建（20261105）

一句话总结

企业知识库的难点不在模型，而在把文档变成「可被检索的块」：切块 → 向量化 → 存库 → 检索，再配合 OCR 和语音能力处理非结构化资料。

RAG 的基本链路

笔记把 RAG 概括为「五步法」，现场明确写下的环节是：

  1. 切块（Chunking）：把长文档拆成适合检索的片段。
  2. 向量化（Embedding）：把文本转成向量。
  3. 存库（Vector Store）：写入向量数据库。
  4. 检索（Retrieval）：按问题召回相关片段，再交给大模型生成答案。

笔记中另有一项 OCR，从上下文看，它承担的是「把扫描件、图片、PDF 变成可切块文本」的前置步骤，很可能就是第五步。这一点属于推断，需对照录音确认。

补充一句笔记原话：「向量是检索」——强调向量化的目的不是炫技，而是为了召回。

切块是关键

笔记在「切块」下面单独写了「大模型切块」，说明现场讨论过用大模型做语义切块，而不是简单按固定字数截断。固定长度切块容易把一句话、一个表格切断；语义切块则按段落主题分界，召回质量更好，代价是处理更慢、成本更高。

实际落地时通常的取舍是：

  • 制度、合同类文档：按条款/章节切，保留标题层级。
  • 手册、FAQ：按问答对切，一问一块。
  • 长报告：先按章节，再在章节内按语义二次切分。
  • 每块都带上来源、页码、章节路径，方便回答时给引用。

一套最小可用的搭建顺序

结合笔记与常规实践，建议按这个顺序做，避免一上来就折腾模型：

  1. 选一个真实场景，例如「公司制度问答」或「产品手册查询」。
  2. 收集 20~50 份文档，先手工确认这些文档里确实有答案。
  3. 做 OCR 与格式清洗，统一成 Markdown 或纯文本。
  4. 按章节 + 语义切块，每块 300~800 字，带来源元数据。
  5. 向量化并入库，先用现成 embedding 模型。
  6. 检索时同时用向量召回和关键词召回，取并集再重排。
  7. 让模型只基于召回内容回答，并强制输出引用来源。
  8. 用 20 个真实问题做评测，记录答对率与「答不出来」的比例。

可以马上做的事

  • 挑一个文档量最小的场景，先跑通「切块 → 检索 → 回答」。
  • 给每个块加来源字段，保证答案可追溯。
  • 建一份 20 题的评测集，量化效果而不是凭感觉。
  • 把 OCR 环节单独验证，确认扫描件的识别质量。
