讲座笔记：RAG——给大模型装一本「可查的书」（20261105）

发表于2026-11-05|更新于2026-11-18
|阅读量:

基于现场速记整理。「五步法」的第五步为推断（OCR），其余四步为笔记明确记录。

一、为什么需要 RAG

大模型有知识，但有两个硬伤：知识有截止日期，而且会一本正经地胡说。

企业场景里这两个问题都致命——你不能让模型用 2023 年的知识回答 2026 年的公司制度，更不能让它在产品手册上瞎编。

RAG（Retrieval-Augmented Generation，检索增强生成）就是为了解决这个：不让模型凭记忆回答，而是先从你的文档库里检索相关内容，再基于检索结果生成答案。

二、RAG 的基本链路

笔记概括为「RAG 五步法」，明确写下的环节有四个：

  1. 切块（Chunking）
  2. 向量化（Embedding）
  3. 存库（Vector Store）
  4. 检索（Retrieval）

另外笔记单独列了一项 OCR。从上下文推断，它应该是整个链路的前置步骤——负责把扫描件、图片、PDF 变成可被切块的文本。所以「第五步」很可能就是 OCR。

三、切块是整个 RAG 的命门

笔记在「切块」下面单独写了「大模型切块」，说明现场专门讨论了这个。

为什么切块这么重要？因为检索的基本单位就是块。块切得不好，后面全白费：

  • 块太大：一个块里塞了好几个话题，检索时召回一堆无关内容。
  • 块太小：一句话被切断，上下文丢失，模型看不懂。
  • 切在段落中间：信息断裂，回答会缺胳膊少腿。

传统做法是按固定字数切（比如 500 字一块），简单但粗暴。「大模型切块」指的是用语义来切——让模型判断哪里是一个话题的边界，按主题分块。代价是慢、费钱，但召回质量明显更好。

实操中的折中：

文档类型 切块策略
制度、合同 按条款/章节切，保留标题层级
手册、FAQ 按问答对切，一问一块
长报告 先按章节，再在章节内语义细分

无论哪种，每条记录都必须带上来源、页码、章节路径，否则回答时无法追溯。

四、向量化与检索：为什么「向量」不是玄学

笔记写了一句很关键的话：「向量是检索」。

这句话的意思是：向量化不是目的，检索才是。把文本转成向量，是为了能用「距离」来衡量两段文本的语义相似度——问题向量和某个块的向量距离越近，说明它俩越相关。

但要注意：纯向量检索不是万能的。有些问题关键词匹配反而更准（比如产品型号、人名、编号）。所以实际工程里通常是向量召回 + 关键词召回，取并集再重排。

六、一套最小可用的搭建顺序

不要一上来就折腾向量库和模型，按这个顺序来：

  1. 选一个真实场景：比如「公司制度问答」或「产品手册查询」。
  2. 收集 20~50 份文档，先确认这些文档里确实有答案。
  3. OCR + 清洗，统一成 Markdown 或纯文本。
  4. 切块 + 来源元数据，每块 300~800 字。
  5. 向量化入库，先用现成 embedding 模型。
  6. 检索：向量 + 关键词并集，重排后取 Top 3~5。
  7. 生成：让模型只基于检索内容回答，强制输出引用来源。
  8. 评测：用 20 个真实问题做评测，记录答对率和「答不出来」的比例。

第 8 步最容易被忽略，但它是唯一能告诉你「这个知识库到底好不好用」的东西。

七、一个常见的误区

很多人以为 RAG 的瓶颈在模型，其实八成的问题出在数据：

  • 文档本身就有过期内容 → 模型如实检索，答案错。
  • 切块没带来源 → 答对了也无法验证，答错了无法追责。
  • 没有评测集 → 你根本不知道效果是好是坏。

模型可以换，但脏数据换不了。所以先把数据搞干净，再谈模型。

这场讲座给我的实际改变

  1. 给所有块加来源字段，保证每个答案都可追溯。
  2. 建一份 20 题的评测集，用答对率而不是感觉来评估。
  3. 向量检索和关键词检索一起用，不迷信单一方案。
  4. OCR 环节单独验证，扫描件识别质量不过关就别往下做。
