讲座笔记：把 AI 变成你自己的工具——本地部署智能体（20261031）

发表于2026-10-31|更新于2026-11-18
|阅读量:

基于现场速记整理。工具名、网址按笔记原样保留；推断与补充已在文中标注。

这场讲座真正的主线

整场讲座的核心不是「怎么用某个 AI 工具」，而是一条更底层的路径：

拿到 API → 用长期提示词约束行为 → 把重复动作脚本化 → 形成自己的自动化工作流。

讲师熊瑞的思路很清晰：不要只在网页里跟 AI 聊天，要把它接进自己的程序。只有接成接口，AI 才能脱离「单次对话」的形态，变成一个可复用、可编排、可无人值守的能力模块。

一、为什么要用 API，而不是网页

网页端的 AI 有两个问题：操作是人点出来的，没法批量；上下文是临时的，换次对话就清零。API 解决这两件事——你可以用脚本批量调用，可以把对话历史和规则持久化。

笔记中反复出现的平台是 Agnes（agnes-ai.cn），它的价值在于：

  • 提供 API Key，让你能用脚本调用。
  • 有视频生成能力（agnes-30-flash 模型），笔记标注「做视频不用钱」——这是它相对于纯文本模型的差异化。
  • 配合 TeleAI 的智能体平台（teleai.com.cn），可以把模型包装成可编排的智能体。

另一个值得注意的细节：笔记提到「用 DeepSeek 来操作 wubuuy 和 telegram」。这说明讲师在用通用大模型当「大脑」，去驱动外部平台（购物、社媒）的操作——这正是 Agent 的典型形态：模型负责决策，接口负责执行。

二、长期提示词：让 AI 有「出厂设置」

这是全场最实用的部分。讲师把它叫「铁律」，并标注为全局最高优先级。

为什么需要这个？因为每次开新对话，AI 都会从零开始。如果你不把行为规则固化，它每次都可能「自由发挥」——改错文件、越权操作、给假答案。长期提示词就是把这些风险前置锁死。

笔记记录的四条规则：

  1. 改文件前必须备份：建 .backup 目录，按模块/功能/时间打 .bak。这一条看起来笨，但它是所有自动化的安全网——AI 改错了，你还有的回滚。
  2. 版本号递增：正式项目每次对话升 0.0.01，有数据库写库、没数据库写 JSON。目的是留痕，出问题能回溯。
  3. 服务启停交给用户：智能体只提示，不直接重启服务，确需操作时等待不超过 3 分钟。这是防止无人值守时误操作导致长时间不可用。
  4. 有依赖的调用串行：并行仅限完全独立的操作，单批不超过 2 个。这是工程经验——依赖关系乱套会导致脏状态。

最后还有一条「回答原则」：不确定就直说，凭经验判断必须标注，每次回答末尾说明哪些确定、哪些待验证。

这套规则的本质是：把 AI 的不确定性显式化。不是让 AI 变得绝对正确，而是让它的错误可见、可回滚、可追溯。

这段提示词的结构值得拆解：

  • 先给文档（Agnes 的 API 文档）——让 AI 有真实依据。
  • 再定配置方式（密钥后台管理）——把不可写死的东西抽出来。
  • 最后列功能并标优先级（对话→图形→视频）。

这其实就是合格的需求文档的写法。反过来想：如果你提需求时跳过前两步，直接说「帮我做个 AI 应用」，AI 只能给你一个模糊的脚手架。

四、附：怎么提出一个好问题

笔记后半段粘贴了一大段「好问题方法论」，这其实是对上面一切的元总结——AI 给不出好答案，往往是因为问题没问好。

四个要素：

  • 差距明确：知道自己不知道什么。
  • 带语境：目的、已知、试过什么。
  • 答案可判定：说清什么样算答对。
  • 有后果：答案会改变你的行动。

再加一条隐藏前提：预设要为真。「为什么大家都不喜欢我」——「大家」和「都」本身就是假预设。

这套方法论不只是给 AI 用的。对人提问、对自己提问，逻辑都一样。

这场讲座给我的实际改变

  1. 注册 Agnes，跑通一次 API 调用，不再只用网页版。
  2. 把「长期提示词铁律」抄进自己所有 AI 项目的系统提示里。
  3. 建立 .backup 目录的习惯——这是成本最低、收益最高的一条。
  4. 写需求时先给文档、再给约束、最后列功能，而不是一句「帮我做个 XXX」。
